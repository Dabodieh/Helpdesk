# Decisions

## Open
| ID | Decision | Notes / default | Owner |
|---|---|---|---|
| D-04 | PostgreSQL row-level security as an additional isolation layer | Not adopted in Phase 2. Isolation layers in place: fail-closed EF scope filter, composite foreign keys, per-action `IAuthorizer` checks, and the Phase 1 + Phase 2 isolation matrices (no leak found). Re-evaluate before production hardening or if a new bypass path appears. | Principal |
| D-08 | Concrete malware-scanning engine (e.g. ClamAV, commercial API, cloud scanner) | Scanning is **required before any production release that accepts user attachments**. Engine choice not blocking until Phase 3. Abstraction: `IAttachmentScanner` (see SECURITY.md).  Phase 3: the scan seam and the `Attachments:RequireCleanScan` download gate exist; no engine yet. | Principal / PO |
| D-09 | Data retention policy (periods, export, anonymisation, legal hold) | Organisational/compliance policy, **unresolved**. No automatic deletion, no age-based hard-delete. Schema must keep later retention/export/anonymisation possible. PROVISIONAL periods proposed 2026-10-07 (post-review D7) in `docs/plans/POST-REFINEMENT-10-DECISIONS.md`; they must be checked against the approved organisational retention policy; no destructive retention until approved. | PO / compliance |
| D-11 | Platform-admin self-granting department membership | **Closed by S-02 / ADR-039:** self-assignment is allowed and needs no separate approval; it stays audited (`selfGrant`, `viaPlatformAdmin`). | PO |
| D-12 | Future audited emergency ("break-glass") ticket access | Moot for the Platform Administrator (global access, S-02). | PO |
| D-19 | Privacy notice and record of processing for Platform Administrator access to all ticket content (S-02) | **Open, not assumed approved.** Draft wording in `docs/guides/TICKET_CONTENT_ACCESS.md`. Needs organisational (data-protection) approval before the notice is published. Also open: whether Platform Administrator reads of ticket content are individually logged. | PO / DPO |
| D-16 (OPEN; Refinement 3 real-tenant run BLOCKED: no approved tenant configuration, see docs/guides/GRAPH_TENANT_VALIDATION.md) | Close the ADR-011 production validation gate (ADR is Accepted as design direction; production readiness conditional on real-tenant validation) | Requires a test tenant + shared mailboxes + Exchange admin (runbook `docs/guides/GRAPH_TENANT_VALIDATION.md`). Gate stays OPEN until the runbook has run successfully against an approved test mailbox. Blocks Phase 3 production email readiness, not Phase 2. | Principal / PO |
| D-18 | Automatic shared-mailbox creation | Not built. Needs a separate Exchange Online management identity (not the mail application), a role limited to creating shared mailboxes, an approved process and a tenant to validate against. Until then the Microsoft 365 page prepares a script for a tenant administrator (ADR-035). | Principal / tenant admin |
| D-19 | Polling-only mail for local Docker (no public HTTPS) | With `Mail:Provider=Graph` startup requires a public https `Mail:NotificationBaseUrl`; subscriptions are made on registration. The 5-minute reconcile already finds mail without a subscription, but a mailbox without one reports `subscription_*` attention and registration would try to create it. Allowing an explicit polling-only mode changes startup validation and mailbox health semantics: needs a decision. | Principal |

## Resolved
| ID | Decision | Resolution |
|---|---|---|
| D-14 | User (de)activation | **Resolved 2026-10-15 (S-01).** Platform administrators deactivate and reactivate accounts (`PUT /api/platform/users/{id}/active`): audited, never self, never the last active platform administrator; deactivation revokes every session for good (session version), releases assigned tickets, and nothing is deleted. Inactive users do not count toward the last-administrator rule. |
| PR10-D22 | Tickets with no stored mailbox | **Resolved 2026-10-07.** Portal submission blocked until the Department has a usable active default mailbox; existing mailbox-less tickets repaired by explicit assignment (Department member with ticket access and `department.mailboxes.manage`; any active usable mailbox of the same Department; correctable only before any public reply is submitted or potentially submitted; confirmation dialog; structured audit, no free-text reason). Full record: `docs/plans/POST-REFINEMENT-10-DECISIONS.md`. |
| D-13 | Persist the ASP.NET Data Protection key ring | **Resolved 2026-10-07 (post-review D2): PostgreSQL**, with a fixed application name. See `docs/plans/POST-REFINEMENT-10-DECISIONS.md`. |
| D-15 | Late reply on a Closed ticket | **Reopen the same ticket** (status Open, same department, reference, team and assignee, audited, system actor). Pending/Resolved also return to Open. No follow-up ticket by default; a per-department setting may change this later. Implemented as `ITicketIngress` (Phase 2); mail ingestion arrives in Phase 3. |
| D-17 | Object store for local dev | **SeaweedFS** (S3-compatible) behind the compose `storage` profile; the app depends only on a generic S3 endpoint. Production provider stays deployment-configurable (Azure Blob via a provider implementation, AWS S3, Cloudflare R2, other). |
| D-01 | Entra tenancy | **Single Entra tenant.** No multi-tenant SaaS auth; no `TenantId` columns in the business domain. Auth infrastructure kept separable so multi-tenant could be designed later. |
| D-02 | Platform admin ticket access | **Reversed by S-02 / ADR-039 (2026-10-16): the Platform Administrator has full access to every department, ticket and Internal Note without membership.** Department roles stay isolated. |
| D-03 | Teams as security boundary | **No (v1).** Departments are the security boundary; teams provide assignment, routing, queues, organisation, workload, reporting. Model must not preclude later team restrictions. |
| D-05 | Requester identity | Per department. |
| D-06 | Ticket numbering | `KEY-n` per department. |
| D-07 | Department mailboxes | **Exchange Online shared mailboxes**, accessed by the application's Entra identity through Microsoft Graph. No mailbox passwords/sessions/interactive sign-in ever. A department may have several; a mailbox belongs to exactly one department in v1. |
| D-10 | Hosting target | Linux + Docker + Compose + PostgreSQL + S3-compatible storage, reverse-proxy compatible, **cloud agnostic**. Entra/Graph are integrations, not hosting requirements. |
