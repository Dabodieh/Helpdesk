# Email Architecture

Module: **Mail** (+ Attachments). Ticketing depends on mail only through contracts; Mail never writes ticket tables directly.

## Inbound pipeline
1. **Webhook** (Graph change notification) → validate `clientState` secret (per subscription), validation-token handshake, reject malformed/oversized; respond 202 fast. Only the notification identifiers are persisted to a `mail.inbound_notification` table (outbox). No processing inline.
2. **Fetch**: a Hangfire job fetches messages for the mailbox using **delta query** (source of truth; webhooks are only a nudge, so lost/duplicate/out-of-order notifications are harmless). A periodic reconciliation delta per mailbox covers missed webhooks and subscription expiry.
3. **Persist raw**: store the message (headers, HTML, text, MIME ref to object storage) as `MailMessage` with unique `(mailbox_id, provider_message_id)` → **idempotency** boundary. Conflict = already processed, skip.
4. **Resolve department**: from the *mailbox* that received it (never from content).
5. **Thread** (see below) → append to existing ticket, or create a ticket + requester, in a single transaction with the `MailMessage` state update and audit event.
6. **Attachments**: validated (size/type/extension/magic bytes), hashed, stored in object storage, scan state tracked; inline images mapped via Content-ID.
7. **Loop/noise protection**: ignore own-mailbox senders, `Auto-Submitted`, `Precedence: bulk/list`, mailer-daemon bounces (bounces recorded against the outbound message instead of creating tickets); per-sender rate limiting.

Failures retry with backoff, then dead-letter into a visible "failed mail" admin list. Nothing is dropped silently.

## Threading
**Policy (Principal decision): a ticket reference in the subject (`[IT-1042]`, `Re: [IT-1042] ...`) is a HINT ONLY.** It is never sufficient evidence to attach an inbound message, alone or combined with "sender is a known participant". Auto-threading requires strong deterministic evidence, in this order:
1. `In-Reply-To` / `References` matched against stored `internet_message_id` of our messages in **the same department**.
2. An opaque outbound correlation token we control (`x-helpdesk-token` header or `[hd:<token>]` body footer), looked up in our own table.
3. Provider conversation id (Graph `conversationId`) within the **same mailbox** only.
4. No strong evidence: do **not** attach. Create a new ticket, or route to manual correlation, and record the subject's candidate ticket reference (receiving department only) as a **suggestion** for the agent. Correspondence is never attached to a possibly wrong, sensitive ticket.
The subject reference may narrow candidate lookup or corroborate steps 1-3, and must never cross departments. Cross-department threading never occurs: evidence pointing into a different department is discarded (treated as new) and logged; a subject reference into another department is not even suggested.
Outbound subjects may still carry `[KEY-1234]` for human recognition; it is documented as a hint and is never relied on for inbound threading. Details: "Graph spike findings" section 9 and ADR-011.

## Outbound
- A public reply is persisted as an outbound `MailMessage` (state `Queued`) in the same transaction as the ticket message (outbox), then sent by a job → provider `SendAsync` from the department mailbox identity (`From` = mailbox address/display name, department signature appended). Retry-safe: send is guarded by a unique outbound id and recorded provider message id; a job that crashed after sending reconciles by looking up the sent item rather than resending.
- Graph constraint: custom `internetMessageHeaders` may only be `x-*`, so `In-Reply-To`/`References` cannot be set directly. Strategy: reply with Graph `createReply`/`createReplyAll` draft on the original message (Exchange sets the threading headers), falling back to `sendMail` plus `X-` headers (the subject may also carry `[KEY-1234]` for human recognition: a hint only, see Threading). Graph also documents a MIME form of `createReply` / draft creation where the caller supplies Internet message headers, which may be a second route to `In-Reply-To`/`References`. Status of R-04 and the open validation steps: see "Graph spike findings" below and ADR-011.
- Record `internetMessageId` of the sent message (read from the draft/sent item) so the requester's reply threads.
- Public replies only ever use the ticket department's mailbox; if the department has no active mailbox, sending fails visibly.
- Internal notes never produce email.

## Graph security and operations
- App registration with **application permissions** limited to specific mailboxes through an Exchange Online **Application Access Policy / RBAC for Applications**, so a compromised credential cannot read other mailboxes.
- Credentials: certificate preferred over client secret; stored in secret store/env, never in DB or logs. Rotation documented.
- Subscription lifecycle: renewal job before expiry, lifecycle notifications handled, re-create on failure; state visible in the admin UI.
- Webhook endpoint: unauthenticated by necessity, therefore validated by `clientState`, strict payload parsing, size limits, rate limit, and idempotent handling (replay-safe). No SSRF surface: the system only calls Graph endpoints from configuration.
- HTML bodies are sanitised on **render** and at ingest (allow-list); remote content/images blocked by default; stored original is immutable.

### 1. Access to a shared mailbox
- **[DOC]** App-only (client credentials) access addresses the mailbox as `/users/{id|upn}/...`; for subscriptions on shared/delegated folders the *application* permission must be used, and the Outlook `*.Shared` permissions explicitly do **not** support notifications on shared folders (notif). Prefer the user **object id** in resource paths; a UPN that begins with a GUID needs the `AAD-UPN:` prefix, otherwise subscription creation can fail intermittently with 503 "Mailbox info is stale" (notif).
- **[DOC]** Scoping: Exchange **RBAC for Applications** replaces Application Access Policies (rbac). Assign scoped *Exchange* application roles (`Application Mail.ReadWrite`, `Application Mail.Send`; `Mail.ReadWrite` does not include send) over a management scope matching only helpdesk mailboxes. Entra-consented application permissions are **unioned** with RBAC grants, so any unscoped `Mail.*` consent in Entra must be removed or scoping is void. Changes take 30 min to 2 h to apply (cached); `Test-ServicePrincipalAuthorization` bypasses the cache (rbac).
- **[MOCK]** Department is derived only from the receiving mailbox (`MailboxRegistry.DepartmentOf`; unknown mailbox throws).
- **[REAL]** E-1 token acquisition and `GET /users/{shared}/mailFolders/inbox/messages` works for a shared mailbox without a licence/sign-in; E-2 a mailbox outside the management scope returns 403 (Test-ServicePrincipalAuthorization says `InScope=False`); E-3 subscription creation and `send`/`createReply` also work under the RBAC-scoped (not Entra-consented) grants; E-4 propagation delay actually observed.

### 2. Reading changes: delta vs notifications
- **[DOC]** `GET /users/{id}/mailFolders/{id}/messages/delta` is per folder; `$select`, `$top`, `$expand` supported, `$filter` only on `receivedDateTime ge/gt`, `$orderby` only `receivedDateTime desc`; query options must be given on the first call only (encoded into the nextLink/deltaLink). Delta also emits `@removed` (deleted *or moved out of the folder*) and read/unread changes; handle them (delta). Least-privileged for delta is `Mail.ReadBasic.All` but that omits body/attachments/headers; we need `Mail.ReadWrite` (+ `Mail.Send`).
- **[DOC]** Webhook subscriptions: resource `/users/{id}/mailFolders('inbox')/messages` (or `/users/{id}/messages`); changeType `created,updated,deleted`; at most 1000 active Outlook subscriptions per mailbox across all apps (notif). Duplicate subscriptions (same resource+changeType) get 409 (hook).
- **[DOC]** Design consequence: notifications are a nudge, delta is the truth; the architecture above stands. Subscribe to `inbox` only (SentItems/Drafts are not ingest sources); deltas run per well-known folder we ingest from.
- **[MOCK]** Notification batch -> de-duplicated fetch targets, mailbox taken from **our** subscription record (not the payload), `clientState` mismatch / unknown subscription rejected (`NotificationProcessor`).
- **[REAL]** E-5 measure notification latency (docs: avg < 1 min, max 3 min); E-6 `created` fires for a message arriving in Inbox but also for moves into Inbox (expected: yes, treat as normal ingest, deduped by idempotency keys); E-7 delta first-round volume/paging on a populated mailbox; E-8 delta token behaviour after long idle (expected: may expire -> full resync; the recovery path must exist); E-9 whether delta `Prefer: IdType="ImmutableId"` is honoured for nextLink continuations.

### 3. Graph message `id` and mutability
- **[DOC]** Default `id` **changes when the item moves** between folders; `Prefer: IdType="ImmutableId"` makes it stable while the item stays in the same mailbox, including folder moves. It still changes if the item moves to an archive mailbox or is exported and re-imported. Ids are case-sensitive. The header applies only to the request carrying it: send it on **every** GET/delta/draft request **and when creating the subscription** (existing subscriptions keep the old format and must be deleted and recreated to switch). `translateExchangeIds` migrates stored ids (imm).
- **[MOCK]** Idempotency primary key `(mailbox, immutable id)`, ordinal (case-sensitive) comparison, scoped per mailbox (`IngestStore`).
- **[REAL]** E-10 verify immutable id is identical in notification, delta, GET, and after moving Inbox -> Archive folder -> Inbox; E-11 verify ids from a subscription created *without* the header differ (negative control).

### 4. `internetMessageId`
- **[DOC]** String in RFC 2822 `<local@domain>` format (msg). A draft already carries one in documented responses (draft, reply).
- **[MOCK]** Normalisation = strip whitespace/angle brackets, compare case-insensitively (`InternetMessageId.Normalize`); nullable (drafts or odd mail may have none); **not unique across mailboxes**: the same inbound mail copied into two helpdesk mailboxes has the same id in both, so every lookup is scoped to the receiving mailbox/department. Fallback idempotency key `(mailbox, internetMessageId)` is guarded by a content fingerprint (subject + from + sentDateTime) so a sender who re-uses one Message-ID cannot make us drop different mail; a mismatch ingests and flags (`IngestOutcome.InternetMessageIdCollisionIngested`).
- **[REAL]** E-12 whether the id Exchange stores on our **draft** is the one on the wire after `send` (expected yes, but Exchange can rewrite Message-ID on submission; this decides whether we can record the id before sending); E-13 how often real inbound mail lacks/duplicates Message-ID in this tenant (sample the mailbox); E-14 case/format changes by gateways.

### 5. `conversationId` / `conversationIndex`
- **[DOC]** `conversationId` = "ID of the conversation the email belongs to"; `conversationIndex` = "position of the message within the conversation" (binary) (msg). Nothing in the docs promises stability across subject changes, mailboxes, or clients.
- **[MOCK]** Rule: never the sole key; used third, **same mailbox only** (a hit in another mailbox is ignored; in another department it is also reported). A fixture shows a subject-change reply that carries a *new* `conversationId` yet still correlates via `In-Reply-To`; another shows header-stripped replies where `conversationId` is what rescues threading.
- **[REAL]** E-15 does changing the subject in Outlook/OWA start a new `conversationId` (expected yes: it derives from the conversation topic); E-16 is `conversationId` identical for the same thread in two different mailboxes (expected no, per-mailbox); E-17 does our outbound reply keep the original `conversationId` in Sent Items; E-18 reuse after ticket closure (policy: a closed/reopened ticket decision is **undetermined**, see ADR-011).

### 6. `In-Reply-To` / `References`
- **[DOC]** `internetMessageHeaders` (RFC 5322 header set) is returned only with `$select=internetMessageHeaders` and is read-only (msg). Custom headers may be set only on creation and must start with `x-`; they cannot be edited after sending (msg, draft).
- **[MOCK]** Parsing `References` (oldest first) and matching nearest ancestor first against stored ids of inbound **and** outbound messages, same department only (`CorrelationTests`).
- **[REAL]** E-19 `$select=internetMessageHeaders` returns `In-Reply-To`/`References` for real replies from Outlook, OWA, Gmail, mobile; E-20 how often they are absent in real traffic (expected: rare but real, e.g. gateways, some forwards).

### 7. Reply flow (`createReply` / `reply`), identity, Sent Items
- **[DOC]** `POST /users/{id}/messages/{id}/createReply` returns a draft (`isDraft: true`, new id, `Mail.ReadWrite`); JSON mode accepts `comment` **or** `message.body` (both = 400); in MIME mode the caller supplies headers + content, base64 (reply). `createReplyAll`, single-step `reply` / `replyAll`, `createForward` exist (msg). `POST .../messages/{draftId}/send` (`Mail.Send`) returns 202 with no body and saves to Sent Items (send). With `Prefer: IdType="ImmutableId"` on draft creation the draft's id can be used afterwards to GET the Sent Items copy, which may not exist immediately (imm). Honour `replyTo` if present (reply).
- **[DOC]** `from` = mailbox owner; `sender` = account that generated it; for shared mailbox/delegation they can differ. `from` may be changed only to a mailbox for which the caller has **SendAs**; `sender` only to someone with delegate (send on behalf) rights (compose, msg).
- **[MOCK]** Not covered (no HTTP). Our own rule is encoded in docs only: always send as the ticket's mailbox, never set `from`/`sender` explicitly (no delegation needed, per ADR-010).
- **[REAL]** E-21 `createReply` on a message in a shared mailbox gives `from` = the shared mailbox address (not the app/service principal) under app-only auth; E-22 sent mail arrives with the shared mailbox as visible sender and no "on behalf of" (expected, but confirm; also confirm whether SendAs is needed *in addition to* the RBAC `Application Mail.Send` grant, which is documented as "send as any user" within scope); E-23 the draft carries `In-Reply-To`/`References` (headers fetch via `$select=internetMessageHeaders`) and the sent copy keeps them, plus `conversationId` unchanged; E-24 draft `internetMessageId` equals the one in the recipient's received message (E-12); E-25 Sent Items copy retrievable by the draft's immutable id and how long after `send`; E-26 MIME-mode `createReply` with explicit `In-Reply-To`/`References` is accepted and preserved (fallback for R-04); E-27 `sendMail` with `saveToSentItems` true/false behaviour (not re-fetched in this spike: confirm in the sendMail reference); E-28 add `x-helpdesk-token` on the draft via `PATCH`/create and confirm it survives into Sent Items (documented as creation-time only: verify with `createReply` + PATCH); E-29 `singleValueExtendedProperties` on the draft as alternative.
- **Implication for R-04:** no `x-` header comes back in a customer's reply (mail clients do not echo custom headers), so the custom token mainly serves outbound-send reconciliation (find our own Sent Items copy), bounces/DSNs that quote headers, and body-footer tokens. Inbound threading of customer replies rests on Exchange setting `In-Reply-To`/`References` on the reply draft (E-23).

### 8. Change notifications / webhooks
- **[DOC]** Subscription creation: Graph POSTs `?validationToken=...` to the notification URL; respond within **10 s** with `200`, `text/plain`, URL-decoded token body; otherwise creation fails. Treat the token as opaque (hook). `clientState` (max 128 chars) is echoed in every notification and must be compared (sub, hook). Return `2xx` within **3 s** (queue and return `202`), else Graph retries with exponential back-off for up to **4 h**; a slow endpoint is throttled (marked slow at >10% > 3 s in 10 min) and notifications can be **dropped unrecoverably** (hook).
- **[DOC]** Max subscription lifetime for Outlook message **without** resource data: 10 080 min (just under 7 days); **with** resource data (rich notifications): 1 440 min (just under 1 day); any request under 45 min is raised to 45 min; Graph says requests above the max will fail in future (sub). We use no resource data (no body in webhooks; fewer secrets in transit; no encryption certificate), so renew well inside 7 days (e.g. target 3 days, renew daily).
- **[DOC]** Payload (no resource data): `subscriptionId`, `subscriptionExpirationDateTime`, `changeType`, `resource`, `clientState`, `tenantId`, `resourceData{@odata.type,@odata.id,@odata.etag,id}`; GET returns the **current** state, not the state at notification time (notif, hook). A batch may mix subscriptions. Delivery is at-least-once; the docs contain no ordering guarantee, and no uniqueness guarantee is documented, so assume duplicates and reordering.
- **[DOC]** Lifecycle (`lifecycleNotificationUrl` must be set at creation, cannot be added later; validated like the main URL): `reauthorizationRequired` (respond 202, then `PATCH /subscriptions/{id}` with a new `expirationDateTime` which renews and reauthorises in one call; do not combine `/reauthorize` and `PATCH` within 10 min), `subscriptionRemoved` (recreate, then reconcile), `missed` (full delta resync). Changes between removal/pause and recreation are lost and must be fetched via delta (life).
- **[MOCK]** Duplicate delivery, created+updated collapse, out-of-order batch, forged `clientState`, unknown subscription, and lifecycle -> action mapping (`IngestionTests`).
- **[REAL]** E-30 handshake against our deployed endpoint (public HTTPS, any reverse proxy, no Azure dependency); E-31 observed duplicates/ordering over a few hundred messages; E-32 `created` + `updated` pairs per inbound mail; E-33 lifecycle: force `reauthorizationRequired` by waiting/lowering expiry, confirm PATCH renews; E-34 `missed` cannot easily be provoked, so test delta reconciliation by stopping the endpoint > 4 h or by dropping notifications in a dev proxy; E-35 renewal schedule survives 8+ days.

### 9. Ordered correlation and ingestion rules (adopted for Phase 3; see ADR-011)
Evaluation order for an inbound message, always within the receiving mailbox's **department**:
1. `In-Reply-To`, then `References` (nearest ancestor first) matched against stored `internetMessageId` of our outbound **and** inbound messages (same mailbox preferred).
2. Opaque outbound token (`x-helpdesk-token` header or `[hd:<token>]` body footer), looked up in our own table. Unguessable, unlike ticket numbers.
3. `conversationId`, **same mailbox only**.
4. Subject key `[KEY-n]`: **hint only, never attaches** (not alone, not with a known-participant sender). It may narrow candidate lookup or corroborate 1-3. Without 1-3 the message is not attached: the candidate ticket in the receiving department is recorded as a suggestion (`NeedsReview`, `SubjectHintTicketId`) on the new ticket / manual-correlation item; a candidate in another department is discarded and reported.
5. Otherwise a new ticket (or manual correlation).

Isolation: any evidence pointing at a ticket in another department is discarded, reported (`CrossDepartmentMatchIgnored`) and logged without bodies; the message becomes a new ticket in the receiving department. Evidence pointing to another mailbox of the *same* department attaches for headers/token but is flagged (`MailboxMismatch`); the ticket keeps its own mailbox for outbound identity (ADR-010).
Idempotency keys: `(mailbox, immutable id)`; fallback `(mailbox, normalised internetMessageId)` plus fingerprint. Loop/noise hints (`MailLoopGuard`): own helpdesk address as sender (including other departments' mailboxes), `Auto-Submitted` != `no`, `Precedence: bulk|list|junk`, `X-Auto-Response-Suppress`, `List-Id`/`List-Unsubscribe`, `mailer-daemon`/`postmaster` senders, `multipart/report; report-type=delivery-status`. Note that Sent Items copies never arrive through the Inbox subscription/delta.
- **[MOCK]** All of section 9 (`CorrelationTests`, `IngestionTests`), including: cross-mailbox/cross-department reply never attaches, header match outranks `conversationId`, subject key alone never attaches (also not with a known-participant sender, and not across departments), subject key plus strong evidence attaches by the strong evidence.
- **[REAL]** E-36 end-to-end scenario with two shared mailboxes (A, B) and a requester CC'ing both: the reply to A's outbound mail arrives in A (attaches) and in B (must become a *new* B ticket, not attach to A's); E-37 inter-mailbox auto-reply loop is stopped by the own-address rule; E-38 real `Auto-Submitted`/OOF/DSN header samples match the guard rules.

## Email identity, agent signatures and department acknowledgements (refinement 7) — LOCKED DECISIONS
1. **The ticket's mailbox owns the outbound sender identity.** Every helpdesk reply leaves as `<mailbox display name> <mailbox address>`, whoever sends it. The caller cannot supply a From (the request has no such field; the mailbox is resolved server-side from the ticket, inside its own department: the ticket's mailbox, else the department default, else its only active mailbox, never another department's and never a global sender).
2. **An agent's personal email address is never used as From** (or Reply-To) for helpdesk correspondence. The agent identifies themselves through their signature in the body.
3. **Reply-To is the ticket's helpdesk mailbox address** (set explicitly on the provider draft).
4. **Team, assignee, status and type changes never change the mailbox.** A ticket keeps the mailbox it arrived at. Tickets created by hand (agent) or through the portal store a mailbox at creation: an explicit active mailbox of the department (agents may choose when the department has several), else the default or only one.
5. **Agent signature is per agent, per department** (`agent_signatures`, FK to the department membership with cascade, so it disappears with the membership). It is sanitised HTML (the one allow-list sanitiser of the email model), may use the fixed placeholders `{{agent.name}} {{agent.email}} {{department.name}} {{mailbox.displayName}} {{mailbox.email}}` (unknown ones are rejected on save), and only the owner edits it (`My profile`; a department administrator cannot). It is resolved from the **sending** agent at the moment of sending (Alice's draft sent by Bob carries Bob's) and appended once by the mail outbox to **public replies only**, never to internal notes. No signature for that department means none, never another department's, another agent's or a footer.
6. **There is NO department footer feature.** The old per-mailbox signature column is legacy and unused (kept to avoid dropping data); it is no longer in the API or UI and nothing appends it.
7. **Canned responses and macros are signature-free templates**; a macro reply draft is plain text until an agent sends it, and the signature is added then.
8. **What was sent is immutable.** The outbound `mail.messages` row stores the exact HTML (reply text plus the signature resolved at send time) and the plain-text equivalent; later edits of a signature or template never change it.
9. **Department acknowledgements** (`department_auto_replies`): one configuration per department (enabled, email-created and/or portal-created, subject and body templates with the placeholders `{{requester.name}} {{ticket.reference}} {{ticket.subject}} {{department.name}} {{mailbox.displayName}} {{mailbox.email}}`; no loops, conditionals or code). **Disabled until configured** (no row = nothing is sent). Each department manages only its own (`department.mailboxes.manage`).
10. **Acknowledgements carry no agent signature** and no ticket message; they are flagged `auto_reply` on the outbound mail row and use the template subject as given.
11. **The template is department-level; the sender is the ticket's mailbox** (an IT ticket arriving at `network@` is acknowledged from `network@` with IT's text). Per-mailbox overrides are not built.
12. **Idempotent and loop-safe:** the acknowledgement is queued inside the transaction that creates the ticket, so one creation yields at most one (a replayed inbound message finds the ticket and never gets there; a lost race rolls it back). Mail the pipeline already ignores (auto-submitted, bounces, bulk, own addresses, mailing lists) never creates a ticket and so is never acknowledged; a requester that is the sending mailbox itself is skipped. A department with no usable mailbox gets an audit entry `ticket.auto_reply_failed` (reason `no_mailbox`); nothing is sent from anywhere else. Delivery uses the normal outbox states, retries and the mail attention list.
13. **Inbound display name:** the sender's display name is presentation metadata, never identity. A real name from a message (not blank, not just the address) replaces the requester's stored name, so the newest useful name wins; a blank or address-only name never overwrites a meaningful one. The address remains the identity, correlation and anti-spoof rules are unchanged.
14a. **Outbound states mean what is known (Refinement 3).** `Sent` = the provider ACCEPTED the message for submission (Graph `send` returned 202 and the draft became a sent item); it is never proof of delivery, and the UI says "accepted for delivery; not confirmed as delivered". `Failed` = definitely not submitted (permanent provider error, mailbox unavailable, retries exhausted) or a CONFIRMED non-delivery report (`last_error = ndr_delivery_failed`). `Uncertain` = the send call failed in a way that leaves the outcome open (connection lost, timeout, 5xx): the sent copy is looked up once; without it the message becomes `Uncertain`, is never re-queued automatically (a draft is persisted before sending, and `submit_started` is saved before the send call so a crashed worker cannot turn into a blind resend), is reported to the ticket as `Uncertain` and listed under Mail needing attention. The dispatcher looks for the sent copy of an Uncertain message once more after 10 minutes (read-only, flag `reconcile_attempted`; never sends): found = marked Sent, otherwise it stays Uncertain for an operator. The ticket message delivery state is explicit (`None, NotDelivered, Pending, Sent, Failed, Uncertain, Bounced`): `Bounced` is a correlated non-delivery report (reported as `delivery_failed`), `Failed` is a message that was not submitted; no consumer compares error strings. Acknowledgements are created with the `x-auto-response-suppress: All` header (the only header class Graph allows on a draft); whether Exchange adds `Auto-Submitted` is a D-16 check (E-37, E-38). A re-delivery with the same Message-ID, subject and sender is a duplicate whatever the time gap. A 429 is certainly not submitted and is retried; 4xx are permanent. An administrator (`department.mailboxes.manage`) resolves an Uncertain message: first the provider is checked (sent copy found = marked Sent, nothing re-sent); only with an explicit "re-send anyway" decision (audited `mail.uncertain_retried`) is it re-queued as a new draft, knowing the requester may receive it twice. The ticket-level "Retry sending" is not offered for it. Ticket users only see a safe category (`MailErrors`): outcome_uncertain, delivery_failed, mailbox_unavailable, authentication, permission_denied, rate_limited, provider_unavailable, rejected_by_provider; the raw provider code stays in `mail.messages.last_error` and the logs.
14b. **Non-delivery reports.** An NDR (mailer-daemon/postmaster sender or `report-type=delivery-status`) is always suppressed: never a ticket, a requester message or an acknowledgement trigger. If, and only if, it names an outbound message of the SAME mailbox by In-Reply-To/References (the sent copy Internet Message-ID) or by our random footer token `[hd:...]`, that message becomes `Failed/ndr_delivery_failed` (audited `mail.delivery_failed_reported`) and the ticket shows "Delivery failed". Subject text is never evidence; an unmatched NDR is only logged by mailbox id. Retrying such a bounced reply is a genuine new send (the old provider draft is cleared, audited `mail.resent_after_bounce`). Delivery reports to the ticket carry a monotonic per-message sequence and the ticket ignores an equal or older one (ADR-016).
14e. **Reply evidence never makes a stranger a party (ADR-017).** Headers, the correlation token and the conversation id only say which ticket an email is about. It attaches only when the sender is the ticket's requester or an active participant; otherwise a NEW ticket is created with an internal note naming the ticket it looked like a reply to, and nothing is written to the original (no message, reopen, participants or requester row). People copied by a party become participants, at most 20 per ticket (the requester and merge-protected requesters are not counted; extra addresses are listed in an internal note); an agent can remove an ordinary participant and the removal is final for the ticket.
14c. **A ticket's mailbox never silently changes.** A ticket that has its own mailbox is answered from it or not at all: when it is inactive the reply is recorded as not delivered (no fallback to the department default or another mailbox). Only tickets without a mailbox use the default.
14d. **Mailbox health** (`GET .../mailboxes`, mailbox administrators only) is derived from persisted state, never probes: Healthy / Attention / Failed / Not set up / Disabled with reason codes (subscription_failed, subscription_expired, subscription_expiring = under 12 h left, so renewal is failing; sync_failing = consecutive failures 1-2 Attention, 3+ Failed; sync_stale = no sync run for 30 min although the sync job runs every 5 min regardless of traffic; outbound_uncertain, outbound_failed, inbound_failed) plus last accepted send. No traffic is never a fault. Healthy is not claimed from configuration alone: it needs a sync that ran.
14e. **Operator recovery.** Subscription expired/failed: the 6-hourly maintenance job recreates it idempotently (one subscription per mailbox); a lifecycle notification triggers a resync. Stale/failing sync: check Graph consent and the management scope; invalid delta tokens already resync from the start (bounded by the not-before window). Uncertain sends: check the mailbox Sent Items, then use Resolve under Mail needing attention.
14. **Production Graph behaviour remains subject to D-16 validation.** Shared-mailbox From, Reply-To, Sender header and Sent Items behaviour are implemented against the documented Graph shapes and the simulator only; they are not proven against a tenant.
15. No tracking pixels or open tracking; audit records only the kind of change (`agent_signature.changed`, `auto_reply.changed`), never the signature or template text.
