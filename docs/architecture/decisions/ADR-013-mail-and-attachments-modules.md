# ADR-013: Mail and Attachments modules, outbox, background jobs

Status: Accepted (Phase 3). Refines ADR-004, ADR-006, ADR-010, ADR-011 and ADR-012. It does **not** change the validation status of ADR-011: behaviour against a real Microsoft 365 tenant is still unvalidated and the production gate stays open.

## Decisions
1. **Modules.** `Helpdesk.Modules.Mail` (schema `mail`: mailboxes, per-mailbox sync state, inbound/outbound messages, webhook receipts) and `Helpdesk.Modules.Attachments` (schema `attachments`: metadata, validation, `IObjectStore`, `IAttachmentScanner`). Migration order: audit 10, identity 20, organisation 30, **mail 35**, ticketing 40, **attachments 50**.
2. **Dependency direction.** Mail depends on Audit, Organisation and Attachments only. Ticketing depends on Mail (and Attachments, Identity, Organisation, Audit). Mail never references Ticketing: it calls it through interfaces that Mail declares and Ticketing implements (`IInboundTicketSink`, `IDeliveryStateSink`, both in `Mail.Contracts`), and Ticketing calls Mail through `IMailboxDirectory` and `IMailOutbox`. Enforced by architecture tests (DAG, internals, public surface).
3. **Department comes only from the receiving mailbox.** `mail.messages.department_id` is copied from the mailbox row (composite FK `(mailbox_id, department_id)`); the sink always receives that department; a ticket's mailbox is constrained by composite FK `(mailbox_id, department_id)` so a ticket cannot point at another department's mailbox. Evidence (headers, token, conversation id) that points into another department is discarded and logged.
4. **Idempotency.** Inbound: unique `(mailbox_id, provider_message_id)`; fallback on `internetMessageId` with a content fingerprint (same content = duplicate and ignored; different content = ingested and flagged `internet_id_collision`). Ticketing writes are idempotent on `(department_id, source, source_ref)` (unique index) with the mail message id as the source reference, so a crash between steps converges without duplicate tickets, messages or attachments (attachments: unique `(department_id, message_id, source_ref)`).
5. **Outbox in the caller's transaction.** A public reply and its outbound mail row commit together: `IMailOutbox.QueueReplyAsync` inserts into `mail.messages` on Ticketing's own connection and transaction (the technique `IAuditWriter` already uses). After the commit the scheduler is nudged; a periodic dispatcher picks up anything missed. Delivery state on the ticket message is `Pending` until the provider accepts the send (`Sent`) or it fails permanently (`Failed`, visible, retryable); with no active mailbox the reply is `NotDelivered`. The provider draft id is persisted **before** sending so a retry after a crash looks for the sent copy instead of sending again. Outcomes are reported to Ticketing through `IDeliveryStateSink` and re-reported by the dispatcher until acknowledged.
6. **Provider seam.** `IMailProvider` (internal to Mail): subscriptions, delta, message/attachment fetch, draft + send, sent-copy lookup. `MicrosoftGraphMailProvider` (Azure.Identity client credentials, plain `HttpClient`, `Prefer: IdType="ImmutableId"`, delta links only followed on the configured Graph host) and `FakeMailProvider` (in-process mailbox simulator, Development/Testing only; startup fails if `Mail:Provider=Fake` elsewhere). The fake reproduces documented shapes and **assumes** Exchange sets `In-Reply-To`/`References` on reply drafts (runbook E-23): that assumption is not validated.
7. **First sync.** Mail received before a mailbox was configured is never imported (delta starts from the configuration time; a delta reset restarts from the same cutoff; already processed mail is skipped by the idempotency key).
8. **Webhooks** are anonymous and CSRF-exempt by explicit metadata (listed in the architecture tests). Authentication is the per-subscription `clientState` (only its SHA-256 is stored, compared in constant time); the mailbox is taken from our subscription record, never the payload; bodies are size-limited and strictly parsed; the response is identical for accepted and rejected notifications. A notification only nudges the delta sync (`dirty` flag), which is the source of truth.
9. **Background jobs.** Hangfire with PostgreSQL storage (ADR-006) is configured **in the Host** only; Mail exposes `IMailJobRunner` (work units) and `IMailJobScheduler` (nudges). Recurring jobs: reconciliation every 5 minutes, dispatch every minute, subscription maintenance every 6 hours. Dashboard read-only and platform-admin only. `Jobs:Enabled=false` (tests) registers no server.
10. **Attachments.** Size cap, blocked executable/script extensions (every dotted part), extension/magic-byte consistency for formats with reliable signatures, sanitised file names, served content type from our own table, always downloaded as an attachment with `nosniff`. Blocked items are recorded without bytes. A `RequireCleanScan` option (default true; false in Development/Testing) makes unscanned items non-downloadable; the scanner is a seam with a no-op implementation until D-08 is decided. Storage is any S3-compatible endpoint (`Storage:Provider=S3`, SeaweedFS locally) or in-memory; nothing is vendor specific.
11. **HTML.** Allow-list sanitisation at ingest (scripts, frames, handlers, remote images removed); the original is kept immutable in Mail and never rendered; the UI shows plain text by default and the sanitised HTML only inside a sandboxed frame with a restrictive CSP.

## New dependencies (approved by this ADR, versions pinned centrally)
Hangfire.AspNetCore + Hangfire.PostgreSql (ADR-006), Azure.Identity (Entra client credentials/certificate for Graph), AWSSDK.S3 (S3-compatible storage), HtmlSanitizer (allow-list sanitising). `Newtonsoft.Json` is pinned to a patched version because Hangfire.Core pulls a vulnerable one transitively.

## Consequences
+ The whole loop (ingest, thread, reply, retry, failure visibility, attachments) is testable without a tenant. + Failure modes are visible (attention list, delivery states) instead of silent. - Real Exchange behaviour (reply headers, draft/sent message ids, shared-mailbox permissions, throttling) is unvalidated. - Raw email bodies are stored in the database (`mail.messages`, retention is part of D-09). - Webhook endpoint has no rate limiting yet (backlog). - Hangfire shares the main database (R-10).
