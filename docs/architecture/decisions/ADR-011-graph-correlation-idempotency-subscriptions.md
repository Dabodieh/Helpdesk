# ADR-011: Graph mail correlation, idempotency keys and subscription policy

Status: Proposed (2026-10-05). Refines ADR-004 and ADR-010. Becomes Accepted once the real-tenant checklist E-1..E-38 in `docs/guides/GRAPH_TENANT_VALIDATION.md` has been run (at minimum E-10, E-12, E-21..E-26, E-36).

## Context
The Phase 1 Graph spike (EMAIL_ARCHITECTURE.md, "Graph spike findings") reviewed the Microsoft Graph contract for shared-mailbox mail and encoded the threading/idempotency rules as mock tests. No tenant was available, so decisions below rest on documentation and on our own logic; behaviours that depend on Exchange are marked for validation.

## Decision
1. **Message identity.** Every Graph request, delta call, draft creation and the subscription itself carries `Prefer: IdType="ImmutableId"`. The Mail module stores that id. Idempotency key: `(mailbox_id, provider_message_id)`; fallback `(mailbox_id, normalised internetMessageId)` guarded by a content fingerprint, which on mismatch ingests and flags rather than drops. All keys are scoped to the mailbox (the same Message-ID legitimately exists in several mailboxes). This matches the unique constraint already in EMAIL_ARCHITECTURE.md and adds the fallback.
2. **Threading precedence** (within the receiving mailbox's department): `In-Reply-To`/`References` against stored inbound and outbound `internetMessageId` -> opaque outbound token (header or body footer, looked up in our own table) -> `conversationId` in the **same mailbox only** -> subject key as weak hint (attaches only for a known participant in the receiving department) -> new ticket. `conversationId` is never the sole key. Evidence pointing into another department is discarded, reported and logged.
3. **Subscriptions.** Without resource data (no bodies through webhooks, no encryption certificate), `changeType=created,updated,deleted` on `/users/{objectId}/mailFolders('inbox')/messages`, `lifecycleNotificationUrl` always set, `clientState` per subscription, target expiry about 3 days (documented maximum is just under 7 days; 1 day with resource data), renewed daily; renewal via `PATCH` only. The mailbox for a notification is taken from our subscription record, never from the payload. Delta remains the source of truth, with periodic reconciliation and a forced reconciliation on `missed` / `subscriptionRemoved`.
4. **Outbound.** Replies use `createReply`/`createReplyAll` drafts (or MIME draft if validation E-26 shows Exchange does not set threading headers), sent as the ticket's mailbox with `from`/`sender` never set explicitly. The draft's immutable id is recorded for Sent Items correlation. A random outbound token is added (header and body footer) for our own correlation. Whether this is enough is validated by E-21..E-29.
5. **Access.** Exchange RBAC for Applications with a management scope limited to helpdesk mailboxes and the application roles `Application Mail.ReadWrite` and `Application Mail.Send`; no Entra-consented unscoped `Mail.*` grants.

## Alternatives considered
conversationId as primary key (not stable across subject change/mailboxes; per-mailbox); resource-data notifications (1-day lifetime, certificate handling, bodies in webhook traffic); one subscription on `/users/{id}/messages` (also fires for Drafts/SentItems noise); mutable default ids (change on folder move).

## Consequences
+ Duplicate/out-of-order/lost notifications are harmless; cross-department attachment is structurally impossible; no delegation permissions needed. - R-04 stays open until E-21..E-26; `x-` headers do not return in customer replies, so threading of customer replies depends on Exchange setting `In-Reply-To`/`References` on the reply; subject-key attachment for participants is retained from the earlier design as a flagged weak signal (if the Principal prefers "hint only", delete the participant branch; one rule and one test change). Reopen/closed-ticket behaviour for late replies is not decided here (D-15).
